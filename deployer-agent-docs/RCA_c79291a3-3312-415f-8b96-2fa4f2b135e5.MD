# RCA — auto-fix-runner (matbakh) production: "server doesn't exist / no dashboard"

## Problem statement
User reports the live site shows "the server does not exist / no dashboard." Preview
(`https://auto-fix-runner--0u1xa2yt.preview.emergentagent.com`) works: 200, `/api/health` ok,
MariaDB alive. Need RCA on production.

## Live production facts (verified)
- Deployed URL: **https://auto-fix-runner.emergent.host**
- Deployment status: **active**, last run `c79291a3-3312-415f-8b96-2fa4f2b135e5` (redeploy) = **success**.
- Template used in prod: **`fastapi_react_mongo_shadcn_base_image`**, `frontend_type=cloudflare`, tier_0, arm64.
- `GET /` → **200**, but body is the **default Emergent template React build** ("Emergent | Fullstack App",
  `/static/js/main.f7415676.js`) — **NOT the matbakh dashboard**.
- `GET /api/health` → **500 Internal Server Error**.
- Backend logs (active run): the pod runs the **stock FARM entrypoint** —
  `Starting FastAPI backend: uvicorn server:app --host 0.0.0.0 --port 8001`.
  `/health` returns **404** on FastAPI, and nginx logs:
  `connect() failed (111: Connection refused) while connecting to upstream, "http://127.0.0.1:8001/health"`.
- Pod events: `Startup probe failed: HTTP probe failed with statuscode: 503` on both replicas at boot;
  pods eventually went Ready (health_check passed only because `/` returns 200 via Cloudflare/R2 and
  `/health` returns a non-5xx 404).

## Root cause
Production was built and is running the **standard FARM template**, not this app's custom runtime.

The app's real stack only exists in the **preview dev runtime**, launched by `npm start` in
`/app/frontend/package.json` → `bash /app/scripts/matbakh-start.sh`, which (a) installs + starts a local
**MariaDB** (`/app/.mysql-data`, debs in `/app/.mariadb-debs`), and (b) runs the built **Node/Express/tRPC**
server (`/app/matbakh/dist/index.js`, built with pnpm) on **port 3000**. `/app/backend/server.py` is only a
reverse proxy forwarding `/api/*` to `127.0.0.1:3000` (`MATBAKH_UPSTREAM_URL`).

In the Cloudflare + k8s production pipeline **none of that custom runtime ever runs**:
1. **Frontend** → the pipeline does a static `yarn build` of `/app/frontend` and serves it from R2 via
   Cloudflare. It served the **default template bundle**, so there is no dashboard UI → the "no dashboard"
   symptom.
2. **Backend** → the pod runs `uvicorn server.py` (the proxy). It forwards `/api/*` to `127.0.0.1:3000`,
   but **no Node server is listening on 3000** → `connection refused` → `/api/*` returns **500**
   ("server doesn't exist").
3. The custom pieces the Node app needs are **gitignored and were never in the pulled source/image**:
   the built `matbakh/dist`, `matbakh/.env` (`DATABASE_URL=mysql://...@127.0.0.1:3306/matbakh`), the
   MariaDB data (`.mysql-data`) and cached debs (`.mariadb-debs`). The `matbakh-start.sh` boot path is
   never invoked in prod, so MariaDB is never installed/started.

Net: the deploy "succeeded" at the pipeline level (static `/` = 200, `/health` = non-5xx 404), but the
served app is the empty template shell with a dead `/api` upstream — exactly the reported symptom.

## Feasibility of running this custom setup in production (as-is): NOT feasible
- In-pod MariaDB is **ephemeral** — data lives in `/app/.mysql-data` inside the container, lost on every
  restart/redeploy/scale event, and there are 2 replicas (each would have its own empty DB). No persistence,
  no shared state.
- `dist`, `.env`, DB data are **gitignored**, so they never reach the build context/image.
- The Cloudflare frontend path builds static artifacts and **cannot run the Node server** that actually
  serves the dashboard.
- tier_0 resources are not sized to install + run MariaDB + a Node server + the FastAPI proxy in one pod.

## Required direction (re-architecture — not a redeploy of the same code)
1. **Backend process**: build `/app/matbakh` (pnpm build) **inside the Dockerfile** and run the Node/Express
   server as the production backend (listening on the platform's backend port, or keep the FastAPI proxy but
   start Node alongside it in the entrypoint). This needs **custom deployment manifests** (Dockerfile +
   entrypoint), not the stock FARM template. `dist` must either be un-gitignored or built in-image.
2. **Database**: replace in-pod MariaDB with an **external managed MySQL/MariaDB** (e.g. managed cloud MySQL /
   PlanetScale). Supply its connection string as a **secret** `DATABASE_URL` (Deployment → Secrets). The
   matbakh `.env` will not ship (gitignored), so every value it holds must become a prod secret.
3. **Frontend**: the matbakh UI must be the thing that gets built/served (served by the Node app, or its
   static build shipped), replacing the default template bundle.

## What I did NOT do
Did not redeploy, did not edit manifests. Eph sandbox could not be used to read source directly (the 1.17 GB
image repeatedly failed to stay running in the sandbox); source structure above is from the reporter's
architecture notes corroborated by the live logs/probes.
